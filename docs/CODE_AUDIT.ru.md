# Аудит FleetOps

Дата ревизии: 2026-08-20.

## Краткий вывод

Функциональный MVP уже полезен, но новые команды добавлялись быстрее, чем развивалась
архитектура. Основные риски находятся не в health-check ядре, а на границах системы:
shell-коллекторы, разбор неструктурированных логов и большой Telegram-роутер.

## Найдено и исправлено в этом обновлении

### Высокий приоритет

- ISO-строки почтового журнала не фильтровались по `--since`: они проходили всегда.
- Ненулевой exit code удаленной команды мог выглядеть как успешный отчет, если команда
  успела что-либо вывести.
- `host.id` без нормализации использовался в имени snapshot-файла.
- Поиск почты принимал неограниченную строку с управляющими символами.

### Средний приоритет

- Парсер Postfix находился внутри Telegram-форматтера, хотя используется как доменная логика.
- `ssh.py`, `formatter.py` и `handlers.py` совмещают слишком много обязанностей.
- Контракт Docker ограничивался сырым `docker ps`; не было health/restart/OOM/stats.
- `/dockerlogs` нельзя было ограничить конкретным контейнером.
- Telegram-сообщения разрезались посередине строк и карточек.

### Низкий приоритет и технический долг

- Большинство диагностик пока возвращает текст, а не типизированный результат.
- CLI и Telegram отдельно перечисляют одни и те же команды.
- DemoCollector вручную повторяет каждый метод Collector.
- Для CLI нет интеграционных тестов парсера аргументов и кодов возврата.

## Целевая структура

```text
fleetops/
  collectors/       только безопасный сбор ограниченных данных
  domain/           модели health, mail и Docker без зависимости от UI
  parsers/          преобразование вывода Linux/Postfix/Docker в модели
  services/         сценарии приложения, валидация и композиция отчетов
  interfaces/       CLI и Telegram как тонкие адаптеры
  security/         redaction и ограничения пользовательского ввода
```
